# 故障排查

## 先跑这两个

```bash
make doctor    # 环境 + 配置自检
make report    # 当前源的状态、分数、地区、最近告警
```

`make doctor` 会逐项报告：Python 版本、依赖、目录、数据库、`GH_TOKEN`、
启用的适配器、地区节点、输出格式。返回非 0 就说明有阻塞项。

---

## 一、构建相关

### `tvbox.json` 没生成 / 没更新

这是**最常见也最正常**的现象。按顺序排查：

1. **被安全阀拦下了。** 日志里会有 `build blocked by the safety valve`，
   `blocked_reason` 是具体原因：

   | 原因 | 含义 | 怎么办 |
   |:---|:---|:---|
   | `NO_ITEMS` | 本轮没有合格源 | 看下面的「源都不合格」 |
   | `BELOW_MIN_SOURCES:2<3` | 条数少于 `output.min_sources` | 加源，或临时调小该值 |
   | `ACTIVE_DROP_85%>70% (20 -> 3)` | 单轮跌幅超过 `output.max_drop_ratio` | 通常是真的挂了这么多源；确认无误后可临时放宽 |
   | `DUPLICATE_URL:...` | 产物里有重复地址（去重没生效） | 报 bug |

   被拦下时 `dist/tvbox.json` **字节级不变**，`dist/last-known-good.json` 和
   `dist/backup/YYYYMMDD.json` 保留上一版。

2. **源不够 3 条。** 初次部署最容易踩。安全阀默认要求 ≥ 3 条。
   往 `data/candidates.json` 加源，或把 `output.min_sources` 临时改成 `1`。

3. **源全都不是 ACTIVE。** 只有 ACTIVE 会被写进产物
   （DEGRADED 要显式开 `output.include_degraded`，FAILED 永不写）。

### 源都不合格

```bash
python -m app.main check --json | head -60   # 看每个源卡在哪一层
```

看 `error_stage`：

| error_stage | 含义 | 典型原因 |
|:---|:---|:---|
| `L1_http` | 连不上 / 非 200 | DNS、超时、被墙、源已下线 |
| `L1_http` + `SSRF_BLOCKED` | 被 SSRF 防护拦下 | 目标是内网/环回/云元数据地址；这是**故意的** |
| `L1_http` + `RESPONSE_TOO_LARGE` | 响应体超过 `max_response_bytes` | 源返回了非配置内容 |
| `L2_config` + `HTML_NOT_JSON` | 返回的是网页 | 多半被反爬拦截，或地址已失效 |
| `L2_config` + `INVALID_JSON` | 不是合法 JSON | 同上 |
| `L2_config` + `UNKNOWN_SCHEMA` | JSON 合法但不是影视仓配置 | 该地址不是配置 |
| `L3_search` | 配置能解析但搜不到 | 源接口有问题；判 DEGRADED |
| `L5_playback` | 搜到但播放地址取不到字节 | 媒资源挂了；判 DEGRADED |

### 源被判死太早 / 太晚

`config/scoring.yaml` 的 `status_thresholds` 和 `lifecycle`：默认 ≥ 70 分 ACTIVE、
≥ 50 DEGRADED、< 50 FAILED；连续 5 次失败暂停输出、12 次判死。

注意有**两条路径**能到 FAILED：分数跌破 `degraded` 线，或者连续失败达到
`fail_mark_failed`。前者通常先发生。

### 源恢复了却不回来

不应该发生（这是修过的 bug），如果遇到请确认：

- `lifecycle.recover_to_active`（默认 5）次连续成功才会回到 ACTIVE；
- 中间只要再失败一次，连击清零，要重新爬。

## 二、发现相关

### 日志：`github adapter disabled: no GH_TOKEN/GITHUB_TOKEN in the environment`

没配 GitHub token，代码搜索适配器被跳过。本地：

```bash
export GH_TOKEN=$(gh auth token)
make discover
```

Actions 里：仓库 Secrets 加 `GH_TOKEN`。

### 什么都发现不了

```bash
python -m app.main discover --json    # 看 found / admitted / rejected
```

- `found: 0` → 适配器没搜到。检查 `config/discovery.yaml` 的
  `enabled_adapters` 和 `code_queries`。
- `found > 0, admitted: 0` → 全被准入拒绝。看 `rejections[]` 里的 reason。
- 只有 `manual` 在跑 → `data/candidates.json` 的 `urls[]` 是空的。

### 同一个源被当成两个

去重键是「规范化 URL 的 sha256」，会抹平
`http`/`https`、`80`/`443`、结尾斜杠、GitHub 的 blob/raw 写法，
并按 `discovery.dedup.tracking_params` 去掉追踪参数。

**已知边界**：只删名单里的参数。`?token=` / `?id=` 这类会被保留——
它们是源正常工作必需的，删掉会让源失效并把不同的源错误合并。

## 三、地区与节点

### 所有源都是 `UNKNOWN`

报告节点数少于 `regions.quorum.min_nodes_for_quorum`（默认 2）。
UNKNOWN 不给惩罚（地区分按中性 50 计），所以单地区部署也能正常工作。

### 远程节点连不上

```bash
python node/probe.py --once --url https://example.com/config.json --allow-private
```

检查 `regions.nodes[].token_env` / `secret_env` 指向的环境变量是否真的存在。
节点不可达会被记录，但**不会**让整轮任务失败（`node_failure_tolerance`）。

## 四、Actions 相关

| 现象 | 原因 / 解决 |
|:---|:---|
| `refusing to allow a Personal Access Token to create or update workflow` | `gh` 缺 `workflow` scope → `gh auth refresh -s workflow` |
| `could not push after 3 attempts` | 两个写库 workflow 撞车。已用 `concurrency: tvbox-data-write` 缓解；重跑即可 |
| pages 一直不触发 | Pages Source 必须选 **GitHub Actions**；且免费账号要求仓库公开 |
| `dist/tvbox.json` 提交了但站点没更新 | 同上，或看 pages workflow 的日志 |
| workflow 卡在 45 分钟超时 | 源太多或某些源很慢。调小 `http.concurrency`、调小 `run_timeout_seconds` |

## 五、数据库

### 库太大

`app.probe_retention_days` 控制原始探测记录保留天数（默认 120）。
`python -m app.main pipeline`（不带 `--no-prune`）会执行清理。

```bash
sqlite3 data/monitor.db "SELECT COUNT(*) FROM probe_results;"
sqlite3 data/monitor.db "VACUUM;"
```

### 库损坏

Actions 上并发提交偶尔会产生冲突版本。恢复：

```bash
git checkout origin/main -- data/monitor.db
```

极端情况可以直接删掉 `data/monitor.db`——它会自动重建，代价是丢掉历史可用率，
源会在几轮之后重新爬回正常分数。

## 六、测试

```bash
make test                                   # 全部
.venv/bin/python -m pytest tests/test_urls.py -q
.venv/bin/python -m pytest -q -k "e2e"
```

测试用真实本地 HTTP 服务和真实 SQLite，**最终链路不使用 mock**。
如果测试挂住，多半是某个网络用例在等超时——`http.max_retries` 越大越慢。

没有 `.venv` 时 `make test` 会用系统 `python3`，可能缺少 pytest：

```bash
make install
```
